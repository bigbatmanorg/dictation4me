# Dictation4me — standing repository instructions for coding agents

1. This checkout already contains the **replacement implementation**. **Do not restart the project, replace code with a scaffold, or reimplement completed modules.** Read `README.md`, `docs/ARCHITECTURE_IMPLEMENTED.md`, `docs/IMPLEMENTATION_STATUS.md`, `design-spec/` and `qualification/acceptance.csv` before making changes.
2. The repository identity stays `bigbatmanorg/dictation4me`, package and CLI stay `dictation4me`. No API/config compatibility with the prior Tk-based prototype is required. Never silently remove installed user data or their credentials. Preserve Git history, user changes and MIT license.
3. NativeHTMLKit use must be through **public Python SDK APIs** only. No Core protocol/private imports, JavaScript, local HTTP server, Tk, Qt, Electron, browser rendering, Node or application plugin framework. Use approved APIs for window/document, live audio via Python/PortAudio, platform shortcuts via explicit OS adapters.
4. Core architecture: independent resident service (microphone, hotkeys, SQLite writes, AI/STT jobs, IPC) + on-demand NativeHTMLKit notebook GUI + optional short-lived CLI. Service continues when GUI closes; `Application.start` reexecutes the backend role.
5. Preserve invariants: bounded durable audio spool, original transcripts immutable, drafts CAS `edit_seq`, AI never overwrites stale edits, persisted delivery attempt before clipboard/send-key, no silent automatic replay after uncertain outcome, expired quick content removed only per policy, failed audio preserved.
6. Provider keys from environment or OS keyring only; no plaintext TOML or log output. Remote provider requires explicit consent. Never offer a TLS validation bypass. All content-bearing API requests should be user-initiated or explicitly opted into auto-transform.
7. Linux KDE Wayland (primary) and Windows x64 must be qualified independently. Headless and simulated SDK tests do not validate real focus, paste, global shortcuts, native microphone, IME or accessibility. Clipboard success and actual insertion are different statuses. Avoid hidden privileged helpers or unapproved uinput/system changes.
8. Run tests, static checks, wheel install, GUI desktop input and failure injection. Update `qualification/runs/` with PASS/FAIL/BLOCKED/NOT RUN, evidence and OS/commit. Never fabricate proof, skip known failures, or claim v1.0 production readiness while native gates are unverified.
9. Continue autonomously: reproduce failures, patch minimally, add regression tests and rerun all affected suites. Prefer no extra services; Docker mock HTTP providers are fine. Do not ask for routine confirmations but do not reset VMs, publish releases, alter other repos, or destroy real data without authorization.
10. Primary handoff prompt: `agent/FINISH_AND_VERIFY.md`. All existing design specifications are retained under `design-spec/`, executable sample contracts under `contracts/`, acceptance cases under `qualification/`.
